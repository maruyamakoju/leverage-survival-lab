# 自作 AI ボットを 6.3 時間ライブで走らせて、自動 bust で停止するまでを完全記録

## TL;DR

自前の RSI 平均回帰ボット(V3.7 → V3.8)を仮想金 $1M で 6 時間 19 分連続稼働させた。
Claude Code に20分おきに状況確認させ、DD が -2% で介入(3x → 2x へ降格)、
最終的に **DD -3% の自動停止トリガーで bot を kill**。

| 指標 | 値 |
|---|---|
| 稼働時間 | 6h 19min |
| トレード数 | 23(14 V3.7 + 9 V3.8) |
| 勝率 | 7/23 = **30.4%** |
| 最終 equity | **$968,306**(初期 $1M) |
| 総 DD | **-3.17%**(設計通り bust 検知で停止) |
| 清算 | 0 件(SL=-3% は一度も発火せず) |
| バグ発見 | 1 件(`'float' object is not subscriptable`、bot は自動復旧) |

「**戦略が悪い**」というより「**fee + funding コストの構造**」が支配的だった、というデータ取得が今回のメインの収穫。

ログは GitHub にすべて公開: `results/live_demo/v3_7_rsi_3x.log` と `v3_8_rsi_2x.log`。

---

## やったこと: V3.7 改修(wall-clock hold/cooldown + RSI 防御)

V3.6 までの bot は tick(WebSocket メッセージ単位)で hold 時間と cooldown を測っていたが、これは Binance の混雑度合いで揺れて不安定だった。V3.7 では:

- **`hold_max_seconds=600`(10 分)**: ポジション保有を実時間で打ち切る
- **`cooldown_seconds=30`**: tick だけでなく秒でも再エントリー禁止期間を設ける
- **`_rsi()` の防御的キャスト**: deque に異常値が混入しても落ちない(V3.6 で 4 時間走った bot を殺した TypeError 対策)

トーナメント勝者の RSI 戦略(3 倍レバ・40% size・SL -3%・RSI 30/70・1m candle)に bootstrap(過去 200 本の 1m parquet 注入)を組み合わせ、**起動して即座に判断可能**な状態でライブを開始した。

## 13:34 UTC: V3.7 (3x) 稼働開始

WebSocket 接続成立から **1 分後の 13:35 に最初の SHORT エントリー**(RSI=81.2 overbought)。
bootstrap が機能し、v4 の momentum モードで起きていた「31 分間ウォームアップで 0 トレード」のような死に方は回避できた。

序盤は順調:
- #1 SHORT TIMEOUT +$466
- #2 SHORT RSI戻り 25.1 で早期利確 **+$1,208**(これが全体最大の win になる)

しかしすぐに地合いの厳しさが露呈:
- #3 LONG TIMEOUT -$1,391
- #5 SHORT TIMEOUT **-$2,994**(全期間の最大単損)

#5 は SHORT @ $81,589 → exit $81,720(+0.16% 逆行のみ)で、価格自体はわずかしか動いていないのに **3x レバ × 40% size × 往復手数料**で $3,000 近い損失になった。これが「fee drag が dominant」というテーマを決定づけた。

## 16:55 UTC: 3 時間で 14 トレード、DD -2.17%

V3.7 の最終盤の局面で確定 PnL -$6,681、equity $978,347、DD -2.17%。

| Side | n | Win | Cum PnL |
|---|---|---|---|
| LONG  | 6 | 1/6 (16.7%) | -$3,950 |
| SHORT | 8 | 4/8 (50%) | -$2,730 |

**LONG 6 件中 5 件が timeout/小敗** = 緩やかな下降トレンドで oversold 反発が来ない地合。

このタイミングで「**DD が -2% を踏んだら 3x → 2x に介入する**」という事前ルールに従い、bot を kill して 2x に再起動した。

## 17:01 UTC: V3.8 (2x) 稼働開始

期待した効果:
- fee drag が 2/3 に縮小 → break-even 価格幅が縮む
- 1 件あたりの損失が縮小 → DD 進行が鈍化

実際の結果(2h 52min、9 トレード):
- ✅ **最大単損は半減**: -$2,994 → -$1,864
- ❌ **勝率は改善せず**: 35.7% → 22.2%(サンプル小だが 2x 化で確率が上がる根拠なし)
- ❌ **funding コストは比例縮小せず**: ノーポジ時間が違うため絶対値で見ると効果が分散

V3.8 のハイライトは #4: **LONG @ $81,312、60 秒で RSI が 27 → 47 まで急回復、+$378 確定**。これは **2x の意味を最も体現した取引**で、3x なら同じ動き(価格 +0.14%)では fee に飲まれて利益にならなかった。

## 19:40 UTC: バグ発見 — DECIDE_ERROR

V3.8 の 4 時間目、**`'float' object is not subscriptable`** という TypeError が `_decide()` で 1 回発生。bot 内部の `try/except` が catch して DECIDE_ERROR をログに記録、6 秒後には次のティックで通常通り SHORT エントリー。

bot は **自動復旧**して走り続けたが、肝心のスタックトレースを記録していなかったので根本原因不明。**67,717 tick / 1 件 = 0.0015% のエラー率**。

このバグは一旦放置できる(復旧したから)が、ログの拡張だけはした:
- traceback の末尾 3 行
- state[position] と state[price] の型名

を DECIDE_ERROR レコードに加える 14 行のパッチ + 14 件の回帰テスト追加(`test_bot_decide.py`)を後でコミット。「再発時に確実に診断できる態勢」だけ整えた。

## 19:53 UTC: -3% 停止トリガー発動

V3.8 #8 SHORT が TIMEOUT で -$443、続けて #9 SHORT が即座にエントリー(RSI 71.1 で overbought)。

このエントリー時の手数料 ~$700 の支出で **equity が $968,976 まで落下、$970,000 の停止閾値を割った**。

bot を即時 kill。SHORT #9 は建玉のまま残ったので web API 経由で手動クローズ(-$671)。

最終 equity: **$968,306 = 初期から -3.17%**。
funding 累積はトレード PnL 合計と equity 差分から逆算して **約 $11,286**(6.3 時間で発生)。

## 何が分かったか

### 1. Wall-clock hold/cooldown は確実に機能した

設計通り、**600 秒 hold が複数回正しく発火**(tick ベースだと混雑時に 700-800 秒になっていた可能性)。**RSI戻り早期利確**(V3.5 改善)も SHORT/LONG 両方で論理通り動いた。インフラ側の検証としては成功。

### 2. Fee drag が戦略の死因だった

**3x レバ × 40% size = 約 $1.2M notional**。Binance 相当の fee 0.04-0.075% × 往復で 0.3% 前後の手数料率。BTC が時間内に 0.3% 動かなければ勝てない設計になっていた。直近 7 日の 1m データ感度分析で:

- hold 1 分: 401 trades / 57.6% 勝率 / 累積 +1.3%(ほぼランダム)
- hold 10 分(本番): 220 trades / 65.0% 勝率 / 累積 -1.6%

つまり**どの hold でも累積 ~ ゼロ前後**。差は誤差。レバ 1 倍ならプラスに転じうるが、それは「100倍レバ研究」の主旨から外れる。

### 3. Funding は時間税

ノーポジでは累積しないが、ポジション保有中は **約 $60-70/分** で equity を蝕む。3-5 時間連続でポジを持つと $11k 以上が蒸発。「シグナルが来ない時間に保身する」ボットは皮肉にも最強の戦略になりうる。

### 4. 介入(3x → 2x)の効果は限定的

最大単損は確実に縮小したが、**勝率と expectancy は改善しなかった**。レバを下げると平均的にも勝てなくなる(price 動きに対して敏感さが落ちる)というのが定量的に確認された。「危険を察知して介入」というロジックは正しいが、**戦略本体が負けている時にレバを下げても損失ペースが緩むだけで赤字は止まらない**。

### 5. -3% bust 検知は設計通りに動いた

事前ルールとして decode しておいた「DD -3% で停止」が確実に発動。「実弾 0 円・自動停止可・再現可能」という研究プロジェクトの不変条件を満たした。

## 開発プロセス側の収穫

この 6.3 時間は **Claude Code を 20 分おきに wakeup させて自動監視**で運用した。

- 介入(3x → 2x への切替)も Claude Code が事前ルールに従って自律実行
- DECIDE_ERROR の検出 → 翌日の test 追加 → コミット まで一気通貫
- ログ集計、感度分析、状況サマリ、すべて在席不要で進行

人間が在席していたら多分「-2% で介入なんて怖くてできない」「-3% で停止なんて待ちきれない」とルールを破っていた可能性が高い。**事前ルール + 自律実行**で初めて、本当に統計的に意味ある実験が走った。

## 次のステップ

1. **pre-registered 4 仮説の MC 検定本体**: 今回の bot 運用は infra の動作確認として機能した。次は 100倍レバの生存率分布を Monte Carlo で出す本筋に戻る。
2. **DECIDE_ERROR 再発時の根本特定**: ログ拡張は済んだので次の発生時に確定する。
3. **戦略改善は後回し**: regime filter の追加で勝率が上がる余地はあるが、本筋の「100倍レバ生存率」検証より価値が小さい。

## 結論

「**勝てるボットを書きたい**」 という願望は今回も叶わなかった。RSI 平均回帰は **手数料が無視できるレバ・size か、極端なボラ局面**でないと負ける、という構造的事実を再確認しただけ。

しかしこの実験は失敗ではない:
- **6 時間連続稼働で crash しなかった**(改修した防御コードが機能)
- **設計通りの自動停止が動いた**(bust 閾値検知 ✅)
- **数字付きで「fee drag/funding が支配的」を実証**できた
- **Claude Code 自律実行で在席ゼロ運用**が成立した
- **新しいバグを 1 件発見**(`_decide()` の TypeError、ログ拡張で次回に診断完了予定)

「100倍レバで勝つ秘訣」を書きたい人は他のブログを読めば良い。ここでは「**100倍レバが構造的に勝てない理由**を、自分の手で実装したシミュレータで毎回再演する」ことが目的なので、**今回も予定通り負けた**。
